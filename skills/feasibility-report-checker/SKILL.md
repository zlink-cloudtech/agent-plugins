# 可行性报告评审（Feasibility Report Checker）

对 spec-analysis 生成的可行性分析报告进行独立质量评审，输出结构化评审报告并标记可自动修复项。

## 前置条件

需要一份已生成的可行性分析报告。用户未提供路径则询问或在 `docs/specs/` 下搜索。

## 工作流程

### Phase 1：读取报告

读取可行性分析报告，重点提取：
- §六 关键风险与约束（逐条编号 R1..Rn）
- §七 未确认假设清单（提取所有 ⚠️ 待确认条目 ID）
- §九 下一步行动表（提取所有行动条目及"来源"列）
- §九 可行性结论（可行/有条件通过/不可行）
- §九 推荐交付路径

### Phase 2：逐维度评审

加载 `references/evaluation-criteria.md`，按三个维度逐项检查：

**维度 1 — 覆盖完整性（40%）**：
1. 提取 §七 所有 ⚠️ 待确认假设 ID，逐一在 §九 行动表"来源"列中搜索 → 记录遗漏项
2. 提取 §六 风险（按序号 R1..Rn），逐一在 §九 行动表"来源"列中搜索 → 记录遗漏或"接受"声明
3. 提取 §六 各风险中内嵌的"**建议**：……"，逐一检查是否流入 §九

**维度 2 — 行动可执行性（35%）**：
1. 逐条检查行动项是否存在需求实现类内容（"实现""开发""编写"等关键词），标记目的偏离项
2. 按类型检查执行建议质量：技术预研须含命令/skill/路径，风险缓解须含措施和验证方式，假设确认须含问题和确认方式，需人工决策须含决策选项和建议方向
3. 检查状态是否初始为"待处理"，阻塞项是否排在前面

**维度 3 — 逻辑一致性（25%）**：
1. 结论与假设/风险状态是否一致
2. 交付路径中阻塞风险是否有对应缓解措施
3. MVP 拆分是否遵循"阻塞风险优先"原则

每个检查项记录 ✅/⚠️/❌ 状态 + 报告摘录 + 问题说明。

### Phase 3：计算评分

按权重计算加权总分：

| 维度 | 权重 |
|------|------|
| 覆盖完整性 | 40% |
| 行动可执行性 | 35% |
| 逻辑一致性 | 25% |

加权总分 = Σ(各维度得分 / 5 × 权重) × 10，满分 10 分。

等级：优秀 ≥ 9.0 / 良好 ≥ 7.5 / 需改进 ≥ 6.0 / 不合格 < 6.0。

### Phase 4：输出评审报告

加载 `assets/report-template.md`，填入评审结果。在"修复建议汇总"中：

- **可自动修复项**：覆盖遗漏（可从 §六/§七 提取建议的）、来源列缺失、结论不一致、排序错误
- **需手动修复项**：§六/§七 信息不完整、执行建议质量过低且不可推断、交付路径与风险根本性矛盾

## 行为规则

- 产物输出到 `docs/specs/` 或用户指定目录，文件名格式：`{report_name}_review.md`
- 每个扣分项必须有具体依据（报告原文摘录），不能凭印象打分
- `[可自动修复]` 标记须准确：只有明确可从报告自身信息修复的项才能标记
- 评审报告面向技能开发者（spec-analysis 的 Phase 4），也面向人工读者，须两者兼顾
