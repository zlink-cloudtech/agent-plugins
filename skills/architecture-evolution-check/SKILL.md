# 架构演进检测

扫描技术规格，判断是否存在需要架构演进才能消解的设计决策，生成演进需求文档。

## 触发条件

以下任一信号出现时建议执行本 Skill：
- 设计中存在突破现有服务边界的接口
- 设计需要新增基础设施组件（存储、消息队列等）
- 设计与 constitution 原则冲突且无法在设计层面消解
- 现有组件能力与需求存在明显差距（差距分析中标记为"需改造"）
- system-design Controller 在 Step 5 输出了 E2 演进信号

## 输入

- 技术规格文档（`docs/specs/techspec-<NAME>.md`）
- constitution 核心原则
- L0/L1 架构地图（现有架构基线）

## 分析步骤

### 1. 逐项扫描

对照技术规格中的"架构分析"节和"接口契约变更汇总"节，逐条判断：

| 信号 | 检查点 |
|------|--------|
| 突破服务边界 | 是否有 SR 要求跨服务直接访问内部资源？ |
| 新增基础设施 | 是否有 SR 引入了新的存储、消息队列、中间件？ |
| constitution 冲突 | 是否有设计决策与原则矛盾？ |
| 能力差距 | 差距分析表中是否有"需改造"条目无法在现有架构内消解？ |

### 2. 分类

- **可内化**：通过修改现有服务内部实现解决，无需架构演进
- **需演进**：需要架构层面变更（修改服务边界、新增基础设施、修改 constitution）

### 3. 输出架构演进需求文档

输出路径：`docs/specs/arch-evolution-<NAME>.md`

```markdown
# [Feature Name] — 架构演进需求

> 来源：`docs/specs/techspec-<NAME>.md`
> 日期：YYYY-MM-DD

## 冲突清单

| ID | 发现位置 | 当前架构约束 | 需求的挑战 | 影响范围 |
|----|---------|-------------|-----------|---------|
| E-N | SR-N / §X | [现有约束或能力描述] | [需求如何突破该约束] | [受影响的服务/流程] |

## 演进建议

| ID | 建议方向 | 优先级 | 不演进的风险 |
|----|---------|--------|------------|
| E-N | [方向描述] | 高/中/低 | [如不演进会导致什么] |

## 升级信息

- 目标接收方：数字转型架构师
- 文档路径：docs/specs/arch-evolution-<NAME>.md
```

### 4. 无演进需求时

输出："当前设计在现有架构约束内可完整实现，无架构演进需求。"，不生成 V1 文档。
