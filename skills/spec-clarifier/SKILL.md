# 需求澄清器（Spec Clarifier）

通过委托子Agent执行10维度歧义扫描，主Agent接收歧义清单后进行逐轮交互澄清。

## 前置条件

需要一份已有的 spec/PRD 文件。如果用户未提供路径，请在继续之前询问。创建新文档请使用 `spec-drafter`。

如果用户提供了额外输入（背景信息、约束条件、重点关注领域），请充分考虑。

## 工作流程

### Phase 1：委托歧义扫描

#### 1a. 加载产品知识上下文

「调用 product-knowledge-sync 技能」，获取产品知识库内容。在委托给子Agent时附上关键产品术语和决策摘要。

#### 1b. 委托子Agent执行10维度扫描

「分发子任务」「在隔离环境中执行」，将完整PRD路径传给子Agent进行扫描：

```markdown
对以下PRD执行10维度歧义扫描。

PRD 路径：[用户提供的路径]
PRD 摘要（≤300字）：
- 功能名：[从PRD提取]
- 核心场景：[1-2句]
- 涉及模块：[列表]

产品知识上下文：
- 产品类型：[来自 product-knowledge-sync]
- 关键术语/决策：[2-3条相关项，避免子Agent误判]

请完整读取 PRD，按以下10个维度逐项扫描：

| 维度 | 检查内容 |
|------|----------|
| 功能范围与行为 | 核心用户目标与成功标准、明确声明的不在范围内、用户角色/画像区分 |
| 领域与数据模型 | 实体、属性、关系；标识与唯一性规则；生命周期/状态转换；数据量级/规模假设 |
| 交互与用户体验流程 | 关键用户旅程/操作序列、错误/空/加载状态、无障碍或本地化说明 |
| 非功能质量 | 性能（延迟、吞吐量目标）、可扩展性、可靠性与可用性、可观测性、安全与隐私、合规/监管约束 |
| 集成与依赖 | 外部服务/API 及其故障模式、数据导入/导出格式、协议/版本假设 |
| 边界情况与故障处理 | 异常场景、速率限制/节流、冲突解决（如并发编辑） |
| 约束与权衡 | 技术约束、明确的权衡或已否决的替代方案 |
| 术语与一致性 | 规范术语表、避免的同义词/已弃用术语 |
| 完成信号 | 可测试的验收标准、可度量的完成定义指标 |
| 杂项/占位符 | TODO标记/未解决的决策、缺乏量化的模糊形容词 |

对每个维度：
- 标注状态：清晰 / 部分覆盖 / 缺失
- 若状态为部分覆盖或缺失，输出：
  - 歧义描述
  - 影响程度：高/中/低
  - 建议问题（选择题格式，2-5个互斥选项；或简答格式，≤5词）

排除条件（不生成问题的歧义）：
- 该澄清不会实质性地改变实现或验证策略
- 该信息更适合推迟到后续规划阶段（标注"推迟"）

输出格式（逐维度）：
## 维度：{名称} — {状态}
<!-- 若状态为部分覆盖/缺失： -->
- 歧义：[描述]
- 影响：高/中/低
- 建议问题：[具体问题 + 选项（如有）]

不要：评估技术可行性、写代码、修改PRD。
```

#### 1c. 接收歧义清单

子Agent返回后，主Agent整理歧义清单，按影响程度排序。若未发现任何歧义，输出"未检测到值得正式澄清的关键歧义。"并结束。

### Phase 2：交互澄清

#### 2a. 筛选Top 5

从子Agent返回的高影响歧义中筛选最多5个问题（影响=高优先，不足5个则选影响=中补足）。

#### 2b. 逐轮提问

**每次只呈现一个问题**。绝不要提前透露后续问题。

**选择题格式：**

分析所有选项，确定最合适的一个，依据：该领域的最佳实践、类似系统的通用模式、风险降低、与文档中可见的明确目标或约束的一致性。

「向用户提问」：
- **推荐：** 哪个选项最佳，附 1–2 句理由
- **选项：** 2–5 个互斥选择
- **自定义答案：** 允许用户提供自己的简短答案（≤5 个词）

**简答格式**（当不存在有意义的具体选项时）：
- **建议：** 一个具体的答案及简要理由
- 用户可以说"是"/"建议"来接受，或提供自己的简短答案

**每次回答后：**
- 若答案清晰，记录到工作记忆；继续下一个排队问题
- 若模糊不清，要求快速消歧——不计入新问题

**当以下情况时停止：** 所有高影响歧义已提前解决、用户发出"停止"/"结束"/"继续"信号、或已提问 5 个问题。

#### 2c. 编码回PRD

每次答案被接受后，立即更新 spec 文件。

**澄清记录章节**（如不存在则创建）：
```markdown
## 澄清记录
### 会话 YYYY-MM-DD
- Q: <问题> → A: <最终答案>
```

**将澄清内容应用到最合适的章节：**

| 答案类型 | 更新目标 |
|----------|----------|
| 功能歧义 | 功能需求 — 添加或更新一个条目 |
| 用户交互 / 角色 | 用户场景或参与者 — 更新场景或添加约束 |
| 数据形态 / 实体 | 关键实体 — 添加字段、类型、关系 |
| 非功能需求 | 成功标准 — 将模糊形容词转换为可度量指标 |
| 边界情况 / 异常流程 | 边界情况章节 — 添加条目（如不存在则创建） |
| 术语 | 统一规范术语；用"（此前称为 X）"标注原文一次 |

- 如果澄清使之前的模糊表述失效，**替换**该表述
- 每次整合后保存文件（原子覆写）
- 保留标题层级；不重新排列无关章节

### Phase 3：完成报告

提问循环结束或用户提前终止后输出：

- 已提问和已回答的问题数量
- 更新后的 spec 文件路径
- 涉及修改的章节（列出名称）
- 覆盖度摘要：

| 分类 | 状态 |
|------|------|
| <分类> | 已解决 |
| <分类> | 推迟（适合后续规划阶段） |
| <分类> | 清晰 |
| <分类> | 未解决（低影响） |

**下一步建议**：

| 条件 | 建议 |
|------|------|
| ≥2 个分类仍为部分覆盖/缺失 **且** 至少一个是中高影响 | **继续澄清** — 再次运行 `spec-clarifier` |

在报告末尾以粗体明确陈述建议。

## 行为规则

- 如果未发现有意义歧义：输出"未检测到值得正式澄清的关键歧义。"并建议继续推进
- 总提问数不得超过 5 个
- 避免推测性技术栈问题，除非其缺失阻碍了功能清晰度
- 尊重提前终止信号："停止"、"结束"、"继续"
- 子Agent委托 prompt 中的 PRD 摘要 ≤300 字
