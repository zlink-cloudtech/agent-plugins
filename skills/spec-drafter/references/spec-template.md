# PRD 模板

在编写 PRD 时使用此结构。不适用的小节直接省略——不要留"不适用"。

---

```markdown
# [功能名称] PRD

## 概述

[1-2 句话概括：该功能是什么，解决什么核心用户问题。]

## 问题陈述

[为什么需要这个功能？它解决了什么痛点或填补了什么空白？]

## 核心价值目标

- [目标 1 — 用户或业务成果，客户关注的价值点的描述]
- [目标 2 -核心价值特性给出的定量的评估标准；比如成本优化目标40%]


## 场景使用约束
 -[明确场景使用的约束，比如语义路由，对于固定工作流场景的模型调用，不适合使用语义路由；比如安装部署暂不考虑其他云平台部署]

## 核心价值场景分析

<!--
  用户故事应按重要性排序的旅程来组织。
  每个用户故事必须可独立测试——哪怕只实现一个，也应当是一个能交付价值的可用 MVP。

  为每个故事分配优先级（P1、P2、P3……），P1 为最关键。
  将每个故事视为一个独立切片，可独立开发、测试、部署和演示。
-->

### 用户故事 1：[角色] [行为]（优先级：P1）

[用通俗语言描述该用户旅程。（xx人员，在xx背景下，做了xx操作，得到了xx预期效果）]


**优先级理由**：[阐述其价值以及为何处于此优先级。]

**价值验收标准**：[描述如何独立测试此场景——例如，"可通过[具体操作]完整测试并交付[具体价值]"]

**验收场景**：

1. **Given** [前置条件]，**When** [用户操作]，**Then** [预期结果]
2. **Given** [前置条件]，**When** [用户操作]，**Then** [预期结果]

---

### 用户故事 2：[角色] [行为]（优先级：P2）

[用通俗语言描述该用户旅程。（xx人员，在xx背景下，做了xx操作，得到了xx预期效果）]

**优先级理由**：[阐述其价值。]

**价值验收标准**：[描述如何独立测试此场景——例如，"可通过[具体操作]完整测试并交付[具体价值]"]

**验收场景**：

1. **Given** [前置条件]，**When** [用户操作]，**Then** [预期结果]

---

[根据需要添加更多用户故事，每个用户故事均需分配优先级。]

## 边界分析

### [容量边界描述]

[产品支持的最大的容量和最小的容量边界说明，比如APIkey支持最大500个]
例如（模型路由支持的最大数量、APIKey支持的最大数量、模型接入最大数量、日志支持保存最长时间，最大条数）

### [输入输出边界描述]

[模块涉及到的一些输入框（文本、数字），需要考虑输入输出边界约束]
例如（模型名称约束 1-256个字符）

### [系统资源约束描述]

[模块实现预计新增占用系统资源的约束：CPU、内存、磁盘空间]
 例如（用量统计模块，新增服务约束：CPU <=2C，内存<=4G，磁盘<=200G）


## 功能需求

### FR-1：[需求名称]

[需求描述。面向业务干系人编写——不含实现细节。]

**验收标准：**
- [ ] [可测试的条件]
- [ ] [可测试的条件]

[每个需求按此格式重复。按顺序编号：FR-1、FR-2……]

## 成功标准

[可衡量的、技术无关的成果。每项必须能在不了解实现细节的情况下验证。]

- [用户或业务成果] 在 [时间 / 比率 / 次数] 内完成
- [指标] 提升 [百分比]
- 系统支持 [数量] 个并发 [实体]


## 假设

[在 PRD 编写过程中做出的合理默认值和推断。]

- **[假设名称]**：[描述及推理依据。]

## 依赖项（可选）

[本功能依赖的其他功能、系统或决策。]

## 待解决问题（可选）

[需干系人在初步评审后给出意见的未解决问题。]
```
