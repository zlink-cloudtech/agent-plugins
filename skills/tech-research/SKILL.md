# 技术预研（Tech Research）

对 PRD 中标记的技术不确定性进行结构化验证，产出预研报告并反馈 PRD 修改建议，形成需求→预研→修改的闭环。

## 前置条件

需要一份已完成评审的 PRD 文件。如果用户未提供路径，请主动询问。

如果 PRD 尚未通过 `spec-checker` 评审，建议先完成评审再启动预研——未评审的 PRD 可能存在结构性问题，导致预研项识别不准确。

## 原则

- **聚焦技术不确定性**：只研究 PRD 中没有明确结论的技术选项、架构决策和可行性问题。不研究 PRD 已有明确结论的内容。
- **判断优先于实施**：预研的目标是帮助决策，而非编写实现代码。原型验证仅用于关键决策项的可行性确认。
- **随时判断是否继续**：发现阻断性风险或研究价值递减时，主动询问用户是否继续。
- **最终反馈到 PRD**：预研结论必须转化为具体的 PRD 修改建议，形成闭环。

## 运行模式

tech-research 支持两种入口：

### 标准模式

入口为 PRD 文件。执行完整流程 Phase 1→2→3→4→5，从 PRD 中自动识别预研项、制定计划、执行研究、输出报告。

由用户直接「调用 tech-research 技能」触发。

### 直接模式

入口为外部传入的预研项列表（已筛选、已关联上下文）。**跳过 Phase 1（识别）和 Phase 2（计划）**，直接从 Phase 3（构造 prompt + 分发子Agent）开始执行。

由 `action-researcher` Agent 「调用 tech-research 技能」，传入预研项列表和来源报告路径。传入参数结构：

```yaml
mode: direct
research_items:
  - id: NX-1
    name: "预研项名称"
    context:
      source: R1               # 来源编号
      description: "风险/假设描述"
      impact: "影响描述"
      execution_hint: "执行建议"
    public_network:
      required: true/false
      resources: ["资源列表"]
    parallel_group: "group-a"      # 可选，不同组可并行
    serial_group: "risk-r1"        # 可选，同组内需串行
    depends_on: ["NX-0"]           # 可选，依赖的上游项 ID 列表
source_report_path: "可行性报告路径"
```

  接收到直接模式请求后，将 `research_items` 视为 Phase 1 的产出，直接进入 Phase 3。
  若调用方已提供 `parallel_group`、`serial_group`、`depends_on`，优先使用这些编排元数据，不重新推断。

> **注意**：直接模式下，Phase 3 的研究 prompt 中"PRD 上下文"替换为"可行性上下文"（使用 `context` 字段），其余流程与标准模式一致。

## 工作流

### Phase 1：读取 PRD，识别预研项

> **直接模式跳过此 Phase，从 Phase 3 开始执行。**

#### 1.1 定位 PRD 文件

如果用户通过 `$ARGUMENTS` 提供了 PRD 文件路径，直接使用。否则搜索当前工作目录下的 PRD 文件（`docs/specs/spec-*.md` 或用户指定的路径）。

#### 1.2 读取并分析 PRD

完整读取 PRD 文件，从以下章节提取技术不确定性：

**主要来源**：
- **技术评估参考**（如有）：直接列出了待评估的技术方案，是预研项的首要来源
- **待解决问题**：明确标记了尚未决策的技术问题，每个条目对应一个预研项
- **依赖项**：依赖的外部系统或能力，需验证可用性和集成方式

**次要来源**：
- **假设**：需要验证才能确认的假设，标记为预研验证项
- **边界分析**：容量/资源约束是否合理需要技术验证
- **功能需求 FR**：涉及工具/库选型的需求（如 FR-2 校验方案、FR-6 镜像方案）

#### 1.3 生成预研项列表

每个预研项标注优先级：

| 优先级 | 定义 | 示例 | 公网访问 |
|--------|------|------|----------|
| **P0** | 架构决策，选错会导致大规模返工 | 执行引擎选型、核心框架选型 | 需判断 |
| **P1** | 核心技术选型，影响功能实现路径 | 校验库选型、调度算法选型 | 需判断 |
| **P2** | 辅助验证，确认 PRD 约束可行性 | 容量边界验证、镜像构建方案 | 需判断 |

**公网访问判断规则**（满足任一即标记为"是"）：
- 需要访问 GitHub / npm / PyPI / crates.io / Maven Central 等公共注册表
- 需要查询外部服务 API 文档、官方文档网站
- 需要拉取/对比外部开源项目的源码、release、issue
- 需要访问 SaaS 产品定价页、功能对比页
- 需要下载外部工具、镜像、二进制文件
- 仅依赖内部系统/内部文档/内部镜像源的预研项标记为"否"

**识别完成后输出预研项摘要**，让用户确认：
```
从 PRD 中识别到以下预研项：

| 序号 | 预研项 | 优先级 | 来源 | 公网访问 |
|------|--------|--------|------|----------|
| 1    | 执行引擎选型 | P0     | §技术评估参考 | 是/否 |
| 2    | YAML Schema 校验方案 | P1 | FR-2 | 是/否 |
| ...

确认后进入 Phase 2，或告知需要调整的项。
```

### Phase 2：制定预研计划

> **直接模式跳过此 Phase。**

#### 2.1 细化每个预研项

为每个预研项定义：
- **研究问题**：需要明确回答的具体问题
- **研究范围**：哪些方面需要研究，哪些不在范围内
- **公网依赖**：是否需要访问公网资源（是/否），如为是，列出具体需要访问的资源
- **预期产出**：结论 + 方案对比（如有多方案）+ 风险等级 + 对 PRD 的影响

#### 2.2 排序和分组

- 按优先级排序（P0 → P1 → P2）
- 按技术依赖排序（有依赖关系的串行执行）
- 标记可并行的预研项组（无相互依赖的项）

#### 2.3 向用户展示预研计划

```
预研计划：

Phase A（并行，无依赖）：
  [P0] 执行引擎选型 — 调研 act vs 自研 🔗公网
  [P1] YAML Schema 校验方案 — 调研 ajv vs zod
  [P1] 进程生命周期管理 — 调研 child_process 最佳实践 🔗公网

Phase B（依赖 Phase A 结论）：
  [P2] 镜像构建方案 — 依赖 CLI 分发方式决策

> 🔗公网 = 需访问公网资源。内网环境无法自动执行，请切换至外网环境完成。

确认后进入 Phase 3，或告知需要调整。
```

### Phase 3：逐步实施预研

#### 3.1 判断并行还是串行

- **标准模式**：按 Phase 2 的计划结果决定哪些项「并行分发」，哪些项「串行分发」
- **直接模式**：优先遵循调用方传入的 `parallel_group`、`serial_group`、`depends_on`
- **有依赖的预研项**：等上游 Agent 返回结果后再启动下游研究

#### 3.1.1 公网环境检测

在「分发子任务」前，执行公网连通性检测：

```bash
curl -s --connect-timeout 3 https://github.com > /dev/null && echo "公网可达" || echo "内网环境"
```

- **公网可达**：所有预研项正常执行
- **内网环境**：
  - 标记为"公网访问: 否"的预研项 → 正常分发执行
  - 标记为"公网访问: 是"的预研项 → **不分发 Agent**，在预研报告中列出"公网访问依赖清单"，提示用户到外网环境完成
  - 「向用户提问」是否继续执行不需公网的预研项：

```
⚠️ 检测到当前为内网环境，以下预研项需要公网访问，无法自动执行：

| 预研项 | 需访问的公网资源 |
|--------|-----------------|
| 执行引擎选型 | GitHub（act 仓库、release） |
| ... | ... |

请切换至外网环境后重新触发预研，或手动完成上述预研项。
是否继续执行不需公网的预研项？（是 / 否）
```

#### 3.2 构造 Agent Prompt

每个研究 Agent 的 prompt 必须包含：

```markdown
研究预研项：[预研项名称]（[优先级]）

{PRD/可行性}上下文：
[相关的 PRD 章节摘录 / 可行性报告上下文，精简到 200 字以内]

公网依赖：[是 / 否]
[如为是，列出需要访问的公网资源及 URL]

研究范围：
- [需要研究的具体方面]
- [需要研究的具体方面]

不需要：
- [明确排除的方面]

## 知识获取工具：DeepWiki

如果你研究的内容涉及 GitHub 开源项目的实现细节（如配置方式、API 用法、架构设计、性能特性等），
可以使用 DeepWiki 工具获取权威信息。DeepWiki 是专门为 GitHub 仓库生成的 AI 驱动知识库。

**可用工具**：

| 工具 | 用途 | 示例 |
|------|------|------|
| `「查询仓库知识库」` | 对指定 GitHub 仓库提问，获取 AI 生成的上下文答案 | "envoyproxy/envoy 如何配置上游负载均衡算法？是否支持随机算法？" |
| `「读取仓库文档结构」` | 查看仓库的文档主题列表，了解有哪些可用文档 | 查看 envoyproxy/envoy 的文档结构 |
| `「读取仓库文档内容」` | 查看仓库的完整文档内容 | 查看 envoyproxy/envoy 的负载均衡配置文档 |

**使用场景**（满足任一即可使用）：
- 需要了解某个开源项目的具体功能支持情况（如"是否支持 X 功能"）
- 需要了解开源项目的配置方式、API 签名、接口契约
- 需要对比开源项目不同版本的功能差异
- 需要了解开源项目的架构设计或实现原理

**不适用场景**：
- 非 GitHub 上的项目或服务（如商业 SaaS 产品的功能对比）
- 需要实时数据或性能 benchmark 的场景（应使用网络搜索或实际测试）
- npm/PyPI 等包注册表的元数据查询（应直接查注册表）

**使用原则**：
- 优先用 `「查询仓库知识库」` 做定向提问，这是最直接高效的方式
- 如果不确定仓库中是否有相关内容，先用 `「读取仓库文档结构」` 浏览主题
- 把 DeepWiki 的回答作为**高质量参考来源**，在"关键发现"中引用
- 若 DeepWiki 未覆盖当前研究涉及的仓库，回退到常规网络搜索

产出格式：
1. 结论（一句话）
2. 方案对比表（如有多方案）
3. 风险评估
4. 推荐
5. 对 PRD 的影响（哪些章节需要调整）
```

**Agent prompt 要点**：
- 给 Agent 足够的 PRD 上下文（精简摘录），但不给整个 PRD（避免上下文膨胀）
- 明确研究范围，防止 Agent 过度探索
- 要求结构化产出，便于后续汇总
- 每个 Agent 独立工作，不共享状态

#### 3.3 分发并行 Agent

对可并行执行的预研项，使用「并行分发」同时发起多个子任务；对串行组使用「串行分发」按顺序执行：

```
子任务 1 → 研究预研项：执行引擎选型（P0）
子任务 2 → 研究预研项：YAML Schema 校验方案（P1）
子任务 3 → 研究预研项：DAG 调度与进程管理（P1）
```

#### 3.4 预研继续判断

在以下时机主动判断是否继续：

- **每个 Agent 返回后**：检查结论是否包含阻断性风险
- **并行组全部完成后**：检查结论是否相互矛盾
- **预研项之间出现未预见依赖时**：调整计划，询问用户

出现以下信号时**询问用户**是否继续：
- 发现阻断性风险（如核心技术方案不可行、关键依赖不可用）
- 预研发现与 PRD 核心假设严重冲突
- 某个预研项的研究工作量远超预期（如需要深度原型验证）
- 多个预研项结论都指向"低风险，无可选方案"（预研价值递减）

**用户确认继续后再进入下一个预研组。**

### Phase 4：输出预研报告

#### 4.1 汇总研究结果

将所有 Agent 返回的结果按照 `references/research-report-template.md` 的结构汇总。

#### 4.2 生成报告

加载模板 `references/research-report-template.md`，填入：
- 预研结论摘要表（所有预研项的结论、风险等级、公网访问一览）
- 总体评估（一句话判断技术可行性）
- 每项详细分析（结论 + 方案对比 + 风险评估）
- 关键风险与缓解措施
- 推荐实施路径（按阶段排列）

**公网访问标记**：在摘要表中增加"公网访问"列。若存在公网依赖预研项，在报告末尾追加"公网访问依赖清单"章节，列出需用户到外网环境完成的预研项及所需访问的资源。

#### 4.3 保存报告

- **标准模式**默认输出路径：`docs/specs/research/YYYY-MM-DD-research-report.md`
- **直接模式**默认输出路径：`docs/specs/research/YYYY-MM-DD-action-research.md`

若项目无 `docs/specs/research/` 目录则创建。

### Phase 5：反馈 PRD 修改建议

#### 5.1 对比预研发现与 PRD

加载 `references/prd-modifications-guide.md`，按照指南规则逐项对比：

- 预研结论是否与 PRD 现有假设一致？
- 是否有新发现的依赖需要在 PRD 中记录？
- 是否有 PRD 约束需要调整（放宽或收紧）？
- "待解决问题"是否有已决策项可以标记为完成？

#### 5.2 生成修改建议

每条修改建议包含：
```markdown
## 修改N：[修改标题]

**位置**：§章节名
**修改类型**：新增 / 修改 / 替换 / 删除

**当前内容**：
> [引用原文]

**建议修改为**：
> [修改后内容]

**修改理由**：[预研发现和原因]
```

#### 5.3 保存修改建议

默认输出路径：`docs/specs/research/YYYY-MM-DD-prd-modifications.md`

#### 5.4 完成报告

输出摘要：
```
预研完成。

预研报告：docs/specs/research/YYYY-MM-DD-research-report.md
PRD 修改建议：docs/specs/research/YYYY-MM-DD-prd-modifications.md

共识别 N 个预研项，全部完成。
修改建议 M 条（新增 X / 修改 Y / 替换 Z）。

总体评估：[一句话结论]
```

## 行为规则

- **不跳过 Phase 1 的用户确认**：预研项列表必须让用户确认后再开始研究
- **不研究 PRD 已有明确结论的内容**：PRD 中已经明确的技术选型不需要重复验证
- **不对单个预研项过度深入**：如果 Agent 返回结果足够做决策，不再深挖
- **并行优先**：能并行的预研项不要串行执行
- **Agent prompt 精简上下文**：只给 Agent 相关 PRD 摘录，不给整份文档
- **报告必须包含"对 PRD 的影响"**：每个预研结论都要说明影响 PRD 的哪些章节
- **公网依赖必标记**：Phase 1 识别预研项时，必须为每个预研项标记"公网访问"属性，不可跳过
- **内网降级**：Phase 3 执行前检测网络环境。内网环境下，标记为"公网访问: 是"的预研项不自动执行，输出公网访问依赖清单让用户到外网环境完成；标记为"公网访问: 否"的项正常执行
- **DeepWiki 指引集成**：Phase 3 子Agent prompt 模板中固定包含 DeepWiki 使用指引。子Agent 自行判断何时使用 DeepWiki 工具，主流程不做预判。DeepWiki 仅适用于 GitHub 开源项目的实现细节查询
- **直接模式兼容**：接收到 `mode: direct` 请求时，跳过 Phase 1 和 Phase 2，将 `research_items` 直接转为 Phase 3 的研究任务。「PRD 上下文」替换为「可行性上下文」
- **编排元数据兼容**：直接模式下如已传入 `parallel_group`、`serial_group`、`depends_on`，必须沿用，不重新改写
- **产出路径兼容**：直接模式默认产出 `YYYY-MM-DD-action-research.md`，供 `action-researcher` 与双端制品一致消费
