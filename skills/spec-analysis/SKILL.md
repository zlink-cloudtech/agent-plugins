# 需求可行性分析（Spec Analysis）

从技术可行性角度评估需求，五阶段编排：获取需求 → 并行委托专业 Agent → 合成报告 → 质量门 → 预研衔接。

## 前置条件

接受两种输入形式：
1. **PRD 文件**：已澄清的 PRD 文件路径，用户未提供则询问或在 `docs/` 下搜索
2. **需求描述文本**：用户直接输入的需求描述（如技术需求、优化需求等不需要正式 PRD 的场景），无需文件路径

若输入为需求描述文本，Phase 1 中自行提炼结构化要点（背景、功能点、涉及系统等）；若输入为 PRD 文件，照常读取文件提取结构化内容。

## 工作流程

### Phase 1：获取需求 + 快速否定检查

**若输入为 PRD 文件**：读取 PRD 文件，重点理解：需求背景和业务目标、核心功能点和验收标准（FR）、涉及的系统模块或服务、依赖的外部系统或数据源、Clarifications 节（已确认决策）、Assumptions 节（假设前提）。

**若输入为需求描述文本**：直接以用户提供的描述为输入，自行提炼以下结构化要点：
- 需求背景和目标（1-2 句话概括）
- 核心功能或技术目标（提炼为类 FR 的条目列表）
- 涉及的系统模块或服务
- 依赖的外部系统或数据源
- 隐含的假设前提（从描述中推断，标注为"推断假设"）

无论输入形式，均执行以下**快速否定检查**（先于深度分析）：

| 红灯情况 | 处理方式 |
|----------|----------|
| 违反物理或技术极限（如跨地域毫秒级强一致） | 报告中指出极限，建议调整目标 |
| 约束相互矛盾（如"成本降低10倍且功能翻倍"） | 指出矛盾，要求重新定义约束 |
| 核心约束无依据（如"延迟必须<10ms"无业务来源） | 报告中标记，建议补充数据支撑 |
| FR 之间存在逻辑冲突（如 FR-A 要求零存量影响，FR-B 要求修改同一存储格式） | 指出冲突的 FR 编号和矛盾点，建议 PRD 修正 |

存在红灯 → 输出"⚠️ 需求合理性问题"小节。不存在则继续 Phase 2。

### Phase 2：并行委托专业 Agent

从需求中提取两份摘要（每份 ≤300 字），「并行分发」两个子Agent：

**Agent A — 产品专家**（「委托产品专家Agent」「在隔离环境中执行」）：

```
分析以下需求与现有产品功能的关系，并提取未确认假设清单。

需求摘要：
- 需求背景：[1-2句话]
- 核心功能点（FR）：[列表]
- 涉及的模块/服务：[列表]

输出：

§2 与现有功能的关系：
- 关系判断：互补/替代/独立新增（含具体功能名和边界说明）
- 冲突标记：如与历史决策/约束冲突，列出冲突项及建议
- 信息不足声明：产品知识库无法覆盖时标注"产品知识库信息不足，以下分析基于推断"

§7 未确认假设清单：
从需求的 Assumptions/Clarifications 节（或需求描述中推断的假设）提取以下类型的假设，
判断若不成立是否会影响接口设计、服务边界或数据模型：
- 部署/发布约束 / 技术绑定 / 存储/迁移承诺 / 兼容性承诺 / 外部依赖假设

| ID | 假设来源 | 假设内容 | 若不成立的影响 | 状态 |
|----|---------|---------|--------------|------|
| A-1 | Assumptions/Clarifications | [原文] | [影响描述] | ⚠️ 待确认 / ✅ 已确认 |

若某类型无对应假设，标注"无"。不可省略此节。

不要：评估技术可行性、写代码、输出架构图。
```

**Agent B — 系统架构师**（「委托系统架构师Agent」「在隔离环境中执行」）：

```
分析以下需求的技术依赖、架构影响和关键风险。

需求摘要：
- 涉及的服务/模块：[列表]
- 依赖的外部系统/数据源：[列表]
- 核心数据流描述：[1-2句话]

输出：

§3 前置依赖分析表格：
| 依赖项 | 类型 | 当前架构是否满足 | 说明 |
（类型范围：服务/插件/数据接口/基础设施。满足时说明列可留空，不满足时说明差距和需要做什么）

§4 架构影响：
- Mermaid flowchart（模块级，不到类/函数）展示涉及的系统模块及其交互关系
- 侵入程度判断：旁路新增 / 局部修改 / 核心链路变更

§6 关键风险与约束：
基于依赖分析和侵入评估，识别 Top 3-5 个关键技术风险：
| 编号 | 风险 | 影响 | 缓解方向 |
|------|------|------|---------|
| R1 | [风险描述] | [影响的系统/流程] | [建议缓解方向] |

每个风险附一句话缓解方向。

不要：评估产品合理性、深入代码实现细节、评估复杂度等级。
```

两个 Agent 并行执行。若任一返回不完整或需要补充，追问后再进入 Phase 3。

### Phase 3：合成报告

加载 `assets/report-template.md`，按以下结构填入分析结果，「写入文件」到 `docs/specs/` 或用户指定目录，文件名格式：`{requirement_name}_feasibility_report.md`。
	
	报告头部 **输入来源** 字段：PRD 输入时填 PRD 文件路径，需求描述输入时填"用户需求描述"。

#### 报告结构

**一、需求概述** — 2–3 句话概括。如有需求合理性问题，在此后插入 ⚠️ 小节。

**二、与现有功能的关系** — 来自 Agent A 输出（§2）。若产品知识库信息不足，注明"产品知识库信息不足，以下分析基于推断"。

**三、技术架构前置依赖分析** — 来自 Agent B 输出（§3）。

**四、系统架构影响评估** — 来自 Agent B 输出（§4 的 Mermaid + 侵入程度）。

**五、技术复杂度评估** — 综合 Agent A+B 视角：
- **不可能三角识别**：列出三个核心约束维度（功能完整度/性能/交付速度），判断短期能否同时满足，指出需降级或推迟的维度
- 复杂度评级表：整体复杂度、接口改动范围、数据变更范围、性能/容量风险、兼容性风险（各评低/中/高并附说明）

**六、关键风险与约束** — 来自 Agent B 输出（§6）。使用其编号和格式。

**七、未确认假设清单** — 来自 Agent A 输出（§7）。保持其表格格式。

**阻断规则**：存在任何 ⚠️ 待确认条目时，可行性结论须标注"**有条件通过**"，并明确要求在进入系统设计前完成确认。所有假设已确认则标注"所有假设已在 Clarifications 中确认，无待确认项"。**本节不可省略。**

**八、隐含非功能性需求** — 从需求场景和边界场景推导未被显式写入的非功能性需求。

推导示例：
- 场景"解密失败时后端返回错误，不写入 CRD" → 隐含**原子性**要求
- 场景"公钥获取失败时前端拦截，不发出请求" → 隐含**防御性提交**要求

| ID  | 来源场景/约束 | 隐含 NFR 类型 | 具体要求 | 建议归属服务 |
|-----|------------|------------|---------|-----------|
| N-1 | [场景编号或边界场景] | 原子性/幂等性/时效性/安全性/其他 | [具体要求] | [前端/后端服务名] |

未发现隐含 NFR 时标注"未发现隐含 NFR"。**本节不可省略。**

**九、可行性结论与建议** — 
- **总体判断**（三选一）：可行 / 有条件通过 / 不可行
- **推荐交付路径**：以 MVP 为单位规划迭代，每个 MVP 是独立上线、用户可感知的功能切片。不写技术任务，只写用户视角的交付结果
- **下一步行动**：结构化行动项表格，每条记录可追踪状态，便于后续将结果回填到相关文档。
    - **表格字段**：
      | 字段 | 说明 | 可选值 |
      |------|------|--------|
      | ID | 唯一标识，格式 `NX-{序号}` | NX-1, NX-2, ... |
      | 行动项 | 要完成的具体事项 | 自由文本 |
      | 来源 | 对应的风险或假设编号，无特定来源填 `—` | `R1`..`Rn`、`A-1`..`A-n`、`—` |
      | 类型 | 行动项目的（消除风险/确认假设），可选值见下表 | `风险缓解` / `假设确认` / `技术预研` / `需人工决策` |
      | 执行建议 | 技术预研/风险缓解给出具体命令/skill/路径；假设确认/需人工决策给出参考方向 | 自由文本 |
      | 状态 | 追踪进度 | `待处理` / `已完成` / `已回填` |
    - **类型语义**：
      | 类型 | 目的 | 典型行动 | 执行方式 |
      |------|------|---------|---------|
      | `风险缓解` | 降低或消除已识别风险 | 架构方案选型、性能压测验证、引入防护措施 | Agent 或人工 |
      | `假设确认` | 复核并确认 PRD 假设条件是否成立 | 确认部署约束、验证外部依赖、确认兼容性 | 以人工为主，Agent 可辅助 |
      | `技术预研` | 对技术不确定性调研产出结论 | 调研库/工具选型、API 兼容性、POC 验证 | Agent 可执行 |
      | `需人工决策` | 需产品/业务方做出主观判断 | 功能优先级取舍、接受风险决策、资源分配 | 仅人工 |
    - **编写规则**：
      0. **目的边界约束（硬规则）**：行动项的唯一目的是消除风险和确认假设。
         - ✅ 允许：调研技术方案可行性、验证 API 兼容性、POC 验证、性能压测、确认部署约束、架构方案选型、确认假设条件
         - ❌ 禁止：实现功能模块、编写业务代码、开发接口、数据库建表、前端页面开发 等需求实现类任务
         - 需求实现由后续系统设计和开发阶段完成，不进入行动表
      1. **覆盖验证（生成行动表前执行）**：列出 §六 全部风险项（R1..Rn）和 §七 全部 ⚠️ 待确认假设（A-x..A-y），为每项构造至少一个行动条目并在"来源"列标注对应编号。无法构造行动的项，在风险/假设原文中追加"**接受**：{理由}"，不进入行动表。检查清单：每个 ⚠️ 假设 → ≥1 行动？每个风险 → ≥1 行动或已接受？
         假设确认类行动完成后，须将 §七 中对应假设的状态从 ⚠️ 待确认 更新为 ✅ 已确认。
      2. **风险缓解**条目：须给出具体缓解措施和验证方式，说明缓解后风险等级变化
      3. **假设确认**条目：须指明待确认的具体问题和确认方式（如线下沟通、查阅文档、接口验证），完成后须回填 §七 对应假设状态
      4. **技术预研**条目：须给出具体可操作的命令/skill/文件路径，Agent 可直接执行
      5. **需人工决策**条目：须说明决策选项、影响范围和建议方向，不虚构 Agent 能力
      6. 每个行动项状态初始为"待处理"，完成后可更新为"已完成"，结果回填到 PRD/相关文档后更新为"已回填"
      7. 按优先级排序，阻塞项排在最前
    - **阻断规则**：存在**任何** ⚠️ 待确认假设且对应行动项状态为"待处理" → 结论标注"有条件通过"。所有 ⚠️ 假设已覆盖（有行动项且状态非"待处理"）→ 标注"可行"。有风险被"接受"的 → 在结论中显式列出被接受的风险及理由。

### Phase 4：质量门（自动闭环）

**目标**：确保输出的可行性报告达到"良好"（≥7.5/10）标准，遗漏项自动修复。

4a. **调用 checker**——「调用 feasibility-report-checker 技能」，传入刚生成的报告路径
4b. **评估结果**——读取评审报告：
   - 评分 ≥ 7.5 → 通过，输出最终报告 + 评审分数，Phase 4 结束
   - 评分 < 7.5 → 进入 4c 自动修复
4c. **自动修复**——从评审报告"可自动修复项"中提取问题，按策略修复：
   - **覆盖遗漏**：从 §六/§七 提取被遗漏的待确认假设或风险，生成新行动条目（标注"来源"列），追加到 §九 行动表末尾
   - **来源缺失**：回查 §六/§七，为行动条目补填"来源"列
   - **结论不一致**：根据当前假设/风险状态重新判断并修正结论文字
   - **排序错误**：将阻塞项移动到表格前面，纠正优先级排序
4d. **重新检查**——修复后回到 4a，最多循环 3 轮
4e. **兜底**——3 轮后仍未达标，输出当前报告 + 最后评审报告 + 残留"需手动修复"问题列表，告知用户需人工介入的具体项

**修复边界**：只修改 §九 行动表和 §九 结论文字，不修改 §六（风险）、§七（假设）内容。若评审指出 §六/§七 本身信息缺失，标记为"需手动修复"交由用户处理。

### Phase 5：预研衔接（可选）

Phase 4 质量门通过后执行。

#### 5a：提取可自动执行的行动项

从 §九 下一步行动表中筛选满足以下条件且状态="待处理"的项：
- 类型="技术预研"
- 或 类型="风险缓解"且执行建议中包含 Agent 可执行的具体命令/skill/路径
排除类型="假设确认"和"需人工决策"（这两类以人工执行为主）。若无此类项，跳过 Phase 5。

#### 5b：推荐执行顺序

按依赖关系排序展示：

```
📋 下一步行动中有 N 项可由 Agent 自动完成（技术预研 + 风险缓解）：

| # | ID | 行动项 | 优先级 | 建议顺序 | 理由 |
|----|------|--------|--------|---------|------|
| 1 | NX-1 | ... | P0 | ① 先执行 | 架构决策，阻塞后续项 |
| 2 | NX-3 | ... | P1 | ② 可并行 | 与 NX-1 无依赖 |
| 3 | NX-4 | ... | P2 | ③ 后执行 | 依赖 NX-1 结论 |
```

排序规则：
- P0 项（架构决策）排最前
- 来源列引用相同风险 Rn 的项串行（同风险上下文不可分）
- 来源列引用不同风险/假设的项可并行
- 内容与前面项选型结论相关的排后面

#### 5c：询问用户

「向用户提问」，三个选项：

```
是否立即触发技术预研？

A. 全部触发 — 按建议顺序执行全部可自动执行的行动项
B. 选择触发 — 勾选部分项执行
C. 稍后手动 — 后续通过 /action-researcher <报告路径> 手动触发
```

选择 **B** 时追加多选界面：
```
选择要预研的行动项：
□ NX-1 [描述] [P0] ← 建议优先
□ NX-3 [描述] [P1]
□ NX-4 [描述] [P2] ← 依赖 NX-1
```

选择 **C** 时提示：
```
可随时通过以下方式触发预研：
  /action-researcher docs/specs/{name}_feasibility_report.md
```

#### 5d：委托 action-researcher

「委托 action-researcher Agent」「在隔离环境中执行」，传入：
- 可行性报告路径
- 用户选定的行动项 ID 列表
- 执行顺序建议

#### 5e：处理返回结果

action-researcher 返回后：
1. 读取其输出的状态更新清单
2. 「更新文件」可行性报告 §九 行动项状态（待处理→已完成）
3. 展示摘要：哪些已完成、预研报告路径、修改建议（PRD 修改或需求补充建议）

若 action-researcher 返回了修改建议（PRD 修改或需求描述补充建议），询问用户是否应用。

## 行为规则

- 产物「写入文件」实际创建，输出到 `docs/specs/` 或用户指定目录
- 报告面向产品团队，语言通俗，避免代码术语；必须解释技术概念
- 聚焦"能不能做、有多复杂、影响多大、假设是否成立"，不给代码级方案
- 需求信息不足时明确指出缺失信息要求补充，不猜测
- §7（未确认假设清单）和 §8（隐含 NFR）不可省略
- 快速否定检查不可跳过
- §6 和 §7 来自子Agent输出，直接填入报告，不需要主Agent重新分析
- Phase 5 为可选环节，用户可选择不立即触发预研
